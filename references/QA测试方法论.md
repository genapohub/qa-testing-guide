# 测试 / QA 工程师方案产出指南 · 领域方法论

> 本文档是 `qa-testing-guide` 技能的领域知识库。

---

## 一、场景识别

| 场景 | 名称 | 判断条件（满足任一） | 产出量 | 预估周期 |
|------|------|---------------------|--------|---------|
| 场景一 | 0→1 测试体系建设 | 全新项目/团队、无测试基础设施、需从零搭建测试框架与流程 | 10-12类 | 3-6周 |
| 场景二 | 中大型测试需求 | 新增功能模块的全面测试、新增测试类型(如性能/安全)、测试流程优化 | 6-8类 | 1-3周 |
| 场景三 | 单功能测试/Bug验证 | 单个功能的测试用例补充、Bug的回归测试、测试数据准备 | 2-3类 | 1-2天 |
| 场景四 | 大版本测试策略升级 | 测试框架迁移、自动化覆盖率大幅提升、引入新测试类型 | 8-10类 | 2-6周 |
| 场景五 | 测试技术预研 | 新测试工具评估、测试技术方向探索 | 3-4类 | 1-2周 |

### 识别流程

```
是否全新项目/无测试体系？ → 是 → 场景一
    ↓否
是否测试框架迁移/自动化覆盖率大幅提升？ → 是 → 场景四
    ↓否
是否为工具评估/技术方向探索？ → 是 → 场景五
    ↓否
是否涉及多模块/多测试类型/多环境？ → 是 → 场景二
    ↓否
→ 场景三
```

## 二、场景一：0→1 测试体系建设（12类产出）

### 规划阶段
1. **测试需求分析** — 产品质量要求、上线标准、测试范围、历史Bug分析
2. **测试策略文档** — 测试金字塔定义（单元/集成/E2E比例）、测试类型覆盖（功能/性能/安全/兼容/可访问性）、质量门禁标准
3. **测试工具选型** — 单元测试(框架)、API测试(工具)、E2E测试(工具)、性能测试(工具)、测试管理平台、缺陷管理工具

### 实施阶段
4. **单元测试方案** — 测试框架配置、Mock/Stub策略、覆盖率目标（行≥80%/分支≥70%）、测试文件组织规范
5. **集成/API测试方案** — 接口测试框架、测试数据管理、环境隔离策略、契约测试（Consumer-Driven Contract）
6. **E2E测试方案** — 关键用户路径定义、测试环境管理、测试数据工厂、截图/录屏策略、失败重试机制
7. **性能测试方案** — 性能基准定义（QPS/P95延迟/错误率）、压测场景设计（基准/负载/压力/稳定性）、压测工具选型、压测环境要求、性能回归阈值
8. **安全测试方案** — SAST（静态代码扫描）、DAST（动态安全扫描）、依赖漏洞扫描、安全测试Checklist（OWASP Top 10）

### 流程与基础设施
9. **测试环境管理** — 环境拓扑（dev/test/staging/perf）、数据管理（脱敏/刷新/隔离）、环境拉起/销毁自动化、Mock服务
10. **CI/CD测试集成** — Pipeline中测试阶段设计、质量门禁（覆盖率/通过率/安全扫描）、测试报告生成、失败通知
11. **缺陷管理规范** — Bug生命周期（提交→确认→修复→验证→关闭）、优先级/严重性定义、缺陷分析（根因/趋势/模块分布）
12. **质量度量体系** — 测试覆盖率、通过率、缺陷密度、缺陷逃逸率、MTTR/MTTD、质量Dashboard

## 三、场景二：中大型测试需求（6-8类产出）

1. **测试范围与策略** — 功能模块的测试范围、测试类型选择、风险分析
2. **测试用例设计** — 等价类/边界值/场景法/状态迁移、正常+异常+边界全覆盖、测试数据设计
3. **自动化测试方案** — 自动化范围（哪些适合/不适合自动化）、脚本设计模式（Page Object/Screenplay）
4. **性能测试方案** — 关键接口压测、并发用户模拟、性能瓶颈定位
5. **兼容性测试方案** — 浏览器/设备/系统版本矩阵、测试范围优先级
6. **测试报告模板** — 测试结果汇总、缺陷分布、风险评估、上线建议
7. **回归测试策略** — 回归范围选择（全量/部分/风险驱动）、自动化回归
8. **测试数据与环境** — 数据准备方案、环境申请、数据清理

---

## 四、场景三：单功能测试/Bug验证（2-3类产出）

1. **测试用例** — 功能点拆解、测试步骤、期望结果、测试数据
2. **Bug回归用例** — 修复验证步骤、关联功能回归清单
3. **测试执行记录** — 执行结果、缺陷记录、截图/日志证据

---

## 五、场景四：大版本测试策略升级（8-10类产出）

1. **现状评估** — 当前测试体系痛点、覆盖率现状、缺陷逃逸分析
2. **目标定义** — 升级后目标（覆盖率/自动化率/测试效率）、成功指标
3. **框架选型与迁移** — 新旧框架对比、迁移策略、并行运行方案
4. **测试用例迁移计划** — 迁移优先级、自动化脚本改造、不适用用例处理
5. **自动化测试框架搭建** — 新框架架构设计、工具链整合、CI集成
6. **性能测试基准更新** — 新基准定义、压力模型更新
7. **测试流程优化** — 测试左移/右移、质量门禁优化、反馈效率提升
8. **团队培训** — 新工具培训、最佳实践分享、FAQ文档
9. **过渡期管理** — 新旧并行运行、质量对比验证
10. **效果评估** — 升级前后关键指标对比

---

## 六、场景五：测试技术预研（3-4类产出）

1. **技术调研报告** — 候选工具/框架介绍、社区活跃度、团队匹配度
2. **PoC验证** — 关键场景验证、现有流程兼容性、学习成本
3. **对比评估** — 功能/性能/易用性/生态/成本多维度打分表
4. **推荐方案** — 推荐结论、迁移成本、风险评估

## 七、测试通用规范

### 测试金字塔
```
          ╱  E2E  ╲        10% — 关键用户路径
         ╱  集成/API ╲      30% — 接口/组件/服务间
        ╱   单元测试   ╲     60% — 函数/方法/类
```

### 测试用例编写规范
- 命名：`{被测模块}_{场景}_{预期结果}`
- 结构：前置条件 → 测试步骤 → 预期结果 → 实际结果
- 覆盖：正常路径 + 异常路径 + 边界值 + 权限场景
- 优先级：P0（核心/阻塞）→ P1（重要）→ P2（一般）→ P3（低优）

### Bug 优先级与严重性
| 严重性 | 优先级 | 示例 |
|--------|--------|------|
| 致命 | P0 | 系统崩溃、数据丢失、安全漏洞 |
| 严重 | P1 | 核心功能不可用、数据错误 |
| 一般 | P2 | 非核心功能异常、体验问题 |
| 轻微 | P3 | 文案/UI偏差、优化建议 |

### 性能测试场景模板
| 场景 | 并发 | 持续时间 | 通过标准 |
|------|------|---------|---------|
| 基准测试 | 1 | 5min | P95<目标值 |
| 负载测试 | 预期峰值×1 | 30min | 无错误 |
| 压力测试 | 预期峰值×1.5→2 | 逐步增加 | 找到瓶颈 |
| 稳定性测试 | 预期峰值×0.8 | 4-8h | 无内存泄漏/错误率恒定 |
| 尖峰测试 | 短时×3 | 5min×3轮 | 自动恢复 |

## 八、产出质量检查清单

- [ ] 测试策略覆盖金字塔三层（单元/集成/E2E）
- [ ] 测试类型覆盖充分（功能/性能/安全/兼容性）
- [ ] 测试用例含正常+异常+边界+权限场景
- [ ] 覆盖率目标明确（行/分支/函数）
- [ ] 性能测试含基准+负载+压力+稳定性
- [ ] CI/CD 集成质量门禁（覆盖率/通过率/安全扫描）
- [ ] 缺陷管理规范完整（生命周期/优先级/根因分析）
- [ ] 测试环境可独立拉起/销毁
- [ ] 质量 Dashboard 覆盖核心指标
- [ ] 测试数据脱敏、可刷新

### 去AI味检查
- [ ] 测试用例中有至少 3 个"只有踩过坑才知道要测"的边界场景
- [ ] 自动化测试策略不是"越多越好"——说明了哪些不适合自动化的场景及理由
- [ ] 性能测试的通过标准有具体的 P95/P99 数值
- [ ] Bug 报告不只有步骤和截图——有"为什么我怀疑是这个原因"的分析

## 十、超越AI味：测试工程师的真实直觉

> AI 能生成 100 个测试用例，但真正的QA知道——Bug 从来不躲在教科书里的等价类和边界值。

### 10.1 反AI测试决策五条

**1. 测试用例要有"猎手直觉"**

- 错误做法: 等价类+边界值+判定表（教科书三件套）
- 正确做法: "用户可能在支付时切出去回微信，回来时支付状态可能不一致——加一个切后台->回前台->重查支付状态的用例"

**2. 自动化不是越多越好**

- "核心支付链路自动化（因为不能挂），UI 动画效果手动测（因为自动化脚本维护成本>收益），一次性活动页面不用自动化"

**3. 重现 Bug 比报告 Bug 更重要**

- 错误做法: "步骤：1. 打开页面 -> 2. 点击按钮 -> 3. 观察到报错"
- 正确做法: "步骤：1. 用 iOS 16 的 Safari -> 2. 先登录再退登 -> 3. 不清缓存直接重新登录 -> 4. 点击支付 -> 5. 报 401。怀疑是登出时 token 没清干净"

**4. 性能测试要有"用户视角"的通过标准**

- "P50 < 200ms / P95 < 800ms / P99 < 2s / 错误率 < 0.1%。超过 P99 阈值的请求视为不可接受"

**5. 安全测试要有"攻击者思维"**

- "普通用户A能不能通过改 URL 参数看到用户B的订单？未登录能不能直接调 API？上传文件能不能传 .php 后缀？"

### 10.2 QA 直觉：哪里最容易出 Bug

| 高风险区域 | 为什么 | 测试策略 |
|-----------|--------|---------|
| 时间相关逻辑 | 时区/夏令时/跨天/月末 | 改系统时间测试 + 模拟跨时区 |
| 并发/竞态 | 点击太快/网络慢/切后台 | 连点器测试 + 弱网模拟 |
| 第三方依赖 | SDK版本变更/接口限流/降级 | Mock 异常返回 + 超时测试 |
| 数据迁移 | 字段类型变更/历史脏数据 | 用生产脱敏数据跑迁移脚本 |
| 权限边界 | 越权比功能Bug更致命 | 横向越权 + 纵向越权 |
